# ADR-0002: 本家の更新を取り込みながら日本語化を続けるためのブランチ構成

**状態:** 承認済み

**日付:** 2026-11-12

**決定者:** 開発者

## 背景

このリポジトリはfheroes2のフォークであり、次の3つの作業を、本家の更新を取り込みながら長く続ける。

1. エンジンの日本語対応(CJKの文字表示、原作形式マップの翻訳を読み込む仕組み)
2. 翻訳(`files/lang/ja.po`と、原作形式マップの翻訳データ`files/lang/ja.map-*.tsv`)
3. 新しい勇者やユニットの追加(構想の段階で、未着手)

2026-11-12時点の状態は次のとおりである。

- `master`は本家と同じ内容で、開発者のコミットはない。
- `feature/cjk-support`(エンジンの日本語対応)の上に、`japanese-localization`(`ja.po`だけ)と
  `feature/standard-map-translation-sidecar`(マップ翻訳の仕組みと翻訳データ)が別々に枝分かれしている。
  3つがすべて入ったブランチはない。
- 作業ブランチはどれもリモートへpushしておらず、開発者のPCにしかない。
- 本家は月に約40コミット進む。本家と開発者の両方が変更しているファイルは4つで、
  2026-11-12時点では衝突しない。
- 勇者やユニットの追加で変更する`src/fheroes2/heroes`、`src/fheroes2/monster`、`src/fheroes2/agg`、
  セーブ形式の版番号は、本家も半年で約30回変更しており、最も衝突しやすい。
- 本家から引き継いだGitHub Actionsは、`master`へのpushと`master`向けのPull Requestでだけ動く。

前提として、成果は基本的にこのフォークの中で完結させる。ただし、エンジンの日本語対応と`ja.po`は、
将来本家へPull Requestとして提出できる余地を残す。勇者やユニットの追加は本家へ提出しない。

## 決定事項

### 長く残すブランチ

上流から下流へ、次の順に並べる。

| ブランチ | 役割 | 内容 |
|---|---|---|
| `master` | 本家の鏡 | 本家と同じ内容。開発者のコミットを置かない |
| `ja-engine` | エンジン改造 | 日本語を表示し、翻訳を読み込むための仕組み(C++のコード、ビルド設定、スクリプト、それらの文書)。ゲームの内容は本家と同じ |
| `ja-localized` | 日本語版 | `ja-engine`に翻訳データ(`ja.po`、`ja.map-*.tsv`)を追加したもの。ビルドして遊ぶ対象 |
| `ja-extended` | 日本語版＋独自要素 | `ja-localized`に、勇者やユニットなどゲームの内容を変更するものを追加したもの。着手するときに作成する |

- 翻訳は長く残すブランチを分けず、`ja-localized`から短い作業ブランチを切って戻す。
  `ja.po`と`ja.map-*.tsv`は本家に存在しない独立したファイルであり、履歴を分けなくてもファイル単位で
  取り出せるためである。履歴を分けておく必要があるのは、本家のファイルを変更するコードだけである。
- 原作形式マップの翻訳を読み込むコードは`ja-engine`に置く。「仕組みのコードは`ja-engine`、
  翻訳データは`ja-localized`」と、ファイルの種類だけで置き場所が決定できるためである。
  既存の`feature/standard-map-translation-sidecar`の24コミットは、コードと文書、翻訳データに分け直す。
  これに伴い、ADR-0001の「機構と初回の翻訳データを一体として実装する」は、この決定で置き換える。
- `ja-engine`のビルドは、翻訳データが1つも存在しなくても成功するようにする。ビルド設定は
  翻訳データのファイルを名前で指定せず、存在するものだけをコピーする。`ja-engine`には翻訳データを
  置かないため、特定の言語のファイルを必須にすると`ja-engine`単体でビルドできないためである。
- `ja-extended`を`ja-localized`と分けるのは、ゲームの内容を変更するとセーブデータやマップが本家と
  互換でなくなる可能性があり、「本家と同じ内容の日本語版」を残しておくためである。
  また、勇者やユニットの側の衝突や作成途中の状態が、翻訳の作業を止めないためである。

### 変更の流し方

- 変更は上流から下流へだけ流す。`master` → `ja-engine` → `ja-localized` → `ja-extended`。
  逆向きには流さず、本家を`ja-localized`や`ja-extended`へ直接取り込まない。
  コードの衝突を`ja-engine`で1回解消すれば済むためである。
- `master`は本家へfast-forwardで合わせる。
- それ以外の取り込みはすべてmergeで行い、rebaseしない。ブランチを別のブランチへ取り込むときは、
  fast-forwardできる場合でも`git merge --no-ff`を使う。1つの作業の範囲を履歴に残すためである。
- 短い作業ブランチは`work/<内容>`という名前で、変更を置くブランチ(上の表)から切り、
  `git merge --no-ff`でそのブランチへ戻す。
- 本家へPull Requestを提出するときは、`master`から新しいブランチを切り、`ja-engine`との差分から
  必要な部分を取り出して載せる。`ja-engine`自体は提出用に整形しない。

### 本家を取り込む間隔

月に1回を目安に、作業の区切り(作業ブランチを戻した後)で取り込む。
1回あたりの衝突と、本家の文言変更による`ja.po`のずれを小さく保つためである。

### リモートとpush

- `ja-engine`、`ja-localized`、`ja-extended`は、開発者のフォーク(`origin`)へpushする。
  開発者のPCが故障しても作業が失われないようにするためである。フォークは公開リポジトリであり、
  翻訳途中の状態が公開されることは承知のうえとする。
- `work/*`と`backup/*`はpushしない。

### ビルドの確認

当面は、本家を取り込んだ後と、コードを変更した作業ブランチを戻す前に、開発者の手元でビルドし、
起動と日本語の表示を確認する。`ja-*`ブランチ用のCIは追加しない。必要になった時点で、
本家のワークフローのファイルを変更せず、新しいファイルとして追加する。

## 検討した選択肢

### 作業ごとに長く残すブランチを分ける(エンジン、`ja.po`、マップ翻訳、統合の4本＋`master`)

作業ごとの履歴は分かれるが、本家の取り込みやエンジンの修正を、`ja.po`とマップ翻訳の両方へ毎回
流す必要がある。翻訳データはファイル単位で取り出せるため、履歴を分ける利点が手間に見合わない。

### `master`と統合ブランチの2本だけにする

最も単純だが、エンジン改造と翻訳が同じ履歴に混ざる。本家へ提出するときに、統合ブランチの履歴から
コミットを拾い集めることになり、提出できる余地を残すという前提に合わない。

### 原作形式マップの翻訳を読み込むコードを`ja-localized`に置く

既存の履歴を分け直さずに済む。しかし、仕組みのコードが2つのブランチに分かれ、今後の変更を
どちらへ置くかをその都度判断することになる。分け直しはパス単位で機械的に行え、対象のブランチは
pushしていないため、履歴を書き換えても影響は開発者の手元に限られる。

### ヘッダー行だけの翻訳データを`ja-engine`に置く

ビルド設定を変更せずに`ja-engine`単体でビルドできる。しかし、同じファイルを`ja-engine`と
`ja-localized`の両方が変更することになり、置き場所がファイルの種類ではなく行の種類で決定される。
ビルドが特定の言語の翻訳データを必須にするという不揃いも残る。

### `ja-engine`を本家の最新へrebaseし続ける

`ja-engine`が「本家＋開発者のコミット列」という、そのまま提出できる形で保てる。しかし、rebaseの
たびにコミットが別のものへ入れ替わるため、下流の`ja-localized`も毎回載せ直す必要がある。
取り込みのたびに退避用のブランチとforce pushが必要になり、`--no-ff`で残したマージコミットも失われる。

### 本家を`ja-engine`と`ja-localized`の両方へ直接mergeする

`ja-engine`の衝突の解消を待たずに`ja-localized`を最新にできる。しかし、同じ衝突を2か所で別々に
解消することになり、解消の内容がずれると、後で`ja-engine`を取り込むときにもう一度衝突する。

### 勇者やユニットの追加を`ja-localized`へ入れる

ブランチが3本のままで済む。しかし、「本家と同じ内容の日本語版」が残らず、勇者やユニットの側の
衝突が解消できるまで、本家の取り込み全体が止まる。

### 本家のリリースごとに取り込む

本家が安定と判断した地点に揃えられる。しかし、リリースの間隔は一定でなく
(1.1.17は2026-06-30で、その後4か月以上リリースがない)、間隔が空くと一度に取り込む量が大きくなる。

### 本家のワークフローの対象ブランチに`ja-*`を追加する

本家と同じ検査がすべて動く。しかし、本家がそのファイルを変更するたびに衝突し、
外部サービスの鍵が必要な検査は失敗する。

## 結果

- どのブランチで作業するかが、変更するファイルの種類で決定できる。
- 仕組みと翻訳データの両方が必要な作業は、先にコードを`ja-engine`へ入れて下流へ流し、
  その後に翻訳データを`ja-localized`へ入れる、という2つの段階に分かれる。
- `ja-engine`の履歴にはマージコミットが混ざる。本家へ提出するときは、差分から提出用のブランチを
  作成する手間がかかる。
- 本家を取り込むたびに、`ja-engine` → `ja-localized`(→ `ja-extended`)の順でmergeを繰り返す。
  `ja-extended`を作成した後は、勇者やユニットに関わる衝突を`ja-extended`で解消する。
- 分け直した読み込みコードのコミットのうち、ビルド設定を修正するコミットより前のものは、
  翻訳データがない状態ではCMakeでビルドできない。
- CIがないため、ビルドが壊れたことは開発者が手元でビルドするまで分からない。
- 現在の構成からの移行として、次の作業が必要になる。手順は`docs/BRANCHING.md`に示す。
  - `feature/cjk-support`を`ja-engine`へ、`japanese-localization`を`ja-localized`へ名前を変更する。
  - `feature/standard-map-translation-sidecar`をコードと文書、翻訳データに分け直し、
    前者を`ja-engine`へ、後者を`ja-localized`へ取り込む。分け直した結果を合わせた内容が、
    元のブランチと一致することを差分で確認する。
  - 本家の更新を`master`、`ja-engine`、`ja-localized`の順に取り込む。
  - `ja-engine`と`ja-localized`を`origin`へpushする。
